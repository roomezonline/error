# گزارش جامع ممیزی فروشگاه ErrorService

> این گزارش فقط بر اساس بررسی سورس فعلی، صفحات عمومی، پنل مدیریت، مدل‌های داده و APIهای فروشگاه تهیه شده است. در این مرحله هیچ کد، migration یا داده‌ای تغییر داده نشده است.

## 1. خلاصه مدیریتی

فروشگاه فعلی از نظر پایه‌های یک فروشگاه عملیاتی، وضعیت خوبی دارد: فهرست محصولات عمومی، صفحه جزئیات، علاقه‌مندی، بازدید اخیر، سبد خرید، تسویه‌حساب، پرداخت دستی و آنلاین، کوپن، روش ارسال، رهگیری سفارش، مرجوعی، ارسال مجدد، پرسش‌وپاسخ، دیدگاه و حسابداری پایه وجود دارد.

همچنین چند تصمیم فنی ارزشمند در پروژه دیده می‌شود:

- صفحه مدیریت محصولات pagination سمت سرور دارد.
- API فهرست محصولات فیلتر، مرتب‌سازی و محدودیت `take` دارد.
- سفارش از idempotency key استفاده می‌کند تا دوبار کلیک یا تکرار درخواست سفارش دوم نسازد.
- کاهش موجودی به‌صورت اتمیک انجام می‌شود و سفارش، کالا، مرسوله و رویدادها مدل جدا دارند.
- برای مرجوعی و ارسال مجدد، `OrderReturn`، `OrderShipment` و `OrderEvent` در نظر گرفته شده است.
- قابلیت اعلان موجودی، تاریخچه قیمت، پرسش‌وپاسخ و نظرات محصول وجود دارد.
- برای چند query اصلی فروشگاه migration ایندکس اضافه شده است.

اما ساختار فعلی هنوز بیشتر یک **فروشگاه تک‌انبار، تک‌فروشنده و ساده** است، نه یک Commerce Platform آماده برای هزاران کالا. مهم‌ترین فاصله‌ها در این بخش‌هاست:

1. تعریف مبلغ و حسابداری هنوز قرارداد مالی واحد و شفاف ندارد.
2. مدل محصول برای تنوع کالا، برند، سازنده، بارکد، تأمین‌کننده و چندانبار محدود است.
3. چرخه موجودی، رزرو، ورود و خروج و اصلاحات موجودی دفترکل کامل ندارد.
4. عملیات ادمین در سفارش‌ها خوب شروع شده اما bulk operation، SLA و audit حرفه‌ای ناقص است.
5. پرداخت، بازگشت وجه و تطبیق بانکی به ledger و reconciliation نیاز دارد.
6. مسیر خرید برای مهمان، خطاهای پرداخت، بازیابی سبد و تجربه پس از خرید باید تست سناریویی جدی شود.
7. برای هزاران محصول، جست‌وجوی متنی، facet، cache و گزارش‌گیری باید مرحله‌ای ارتقا پیدا کند.

# 4. بررسی تجربه خرید سایت اصلی

## 4.1 صفحه فهرست محصولات

### نقاط قوت

- عنوان و متادیتای فروشگاهی وجود دارد.
- دسته‌بندی‌ها و breadcrumb وجود دارد.
- hero فروشگاهی و اسلاید محصول دارد.
- جست‌وجو، مرتب‌سازی، فقط موجود، فقط تخفیف‌دار و بازه قیمت وجود دارد.
- صفحه برای موبایل فیلتر جمع‌شونده دارد.
- فهرست محصولات با pagination سمت سرور کار می‌کند.
- API مقدار کل نتایج را با header برمی‌گرداند.
- `take` در API محدود شده و جلوی درخواست‌های بسیار بزرگ را می‌گیرد.

### کمبودها و ریسک‌ها

1. **فیلترها برای فروشگاه بزرگ هنوز محدودند.** فیلتر برند، سازنده، مدل سازگار، نوع قطعه، رنج واقعی موجودی، امتیاز، زمان ارسال و ویژگی‌های فنی دیده نمی‌شود.
2. **جست‌وجو عمدتاً Contains روی نام و توضیحات است.** با چند هزار کالا قابل استفاده است، اما با ده‌ها هزار کالا سرعت و کیفیت پیشنهادها افت می‌کند.
3. **facet و شمارش نتیجه هر فیلتر وجود ندارد.** کاربر نمی‌بیند هر برند یا ویژگی چند نتیجه دارد.
4. **مدل دسته‌بندی فقط نام، آیکون و ترتیب دارد.** slug، والد/فرزند، SEO title، توضیحات، تصویر، وضعیت فعال و ترتیب سلسله‌مراتبی لازم است.
5. **برای کالاهای ناموجود، مسیر تبدیل بازدید به فروش ضعیف است.** اعلان موجودی وجود دارد، اما پیشنهاد جایگزین، مشابه، آخرین قیمت و زمان احتمالی تأمین باید اضافه شود.
6. **صفحه محصول و فهرست ممکن است به cache وابستگی زیادی داشته باشند.** پس از تغییر قیمت یا موجودی باید سیاست invalidation قطعی و قابل مشاهده وجود داشته باشد.
7. **ترتیب پیش‌فرض جدیدترین است.** برای فروشگاه حرفه‌ای باید امکان تنظیم merchandising وجود داشته باشد؛ مثل اولویت تجاری، حاشیه سود، پرفروش، محبوب و موجودی.
8. **سازوکار کنترل محصول تکراری دیده نمی‌شود.** SKU و slug باید یکتا و اجباری یا دست‌کم strongly recommended باشند.

### پیشنهاد حرفه‌ای

- تعریف Catalog مستقل از Inventory.
- اضافه کردن facet بر اساس دسته، برند، ویژگی فنی و محدوده قیمت.
- جست‌وجوی نرمال‌سازی‌شده برای فارسی/عربی، نیم‌فاصله، اعداد فارسی و SKU.
- جست‌وجوی prefix و autocomplete.
- در مرحله رشد جدی، استفاده از موتور جست‌وجوی اختصاصی مثل Elasticsearch/OpenSearch یا سرویس معادل.
- ساخت سیستم `Sort/Boost` مدیریتی برای کنترل ترتیب نمایش.

## 4.2 صفحه جزئیات محصول

### نقاط قوت

- URL عددی و slug پشتیبانی می‌شود.
- canonical، Open Graph و JSON-LD محصول وجود دارد.
- تصویر اصلی و چند تصویر، گالری، swipe موبایل و lightbox وجود دارد.
- قیمت اصلی، تخفیف، زمان تخفیف و وضعیت موجودی نمایش داده می‌شود.
- SKU/کد محصول، تعداد بازدید، امتیاز و نظرات وجود دارد.
- مشخصات فنی ساختاریافته با `ProductSpec` وجود دارد.
- پرسش‌وپاسخ محصول وجود دارد.
- نمودار تاریخچه قیمت وجود دارد.
- علاقه‌مندی، بازدید اخیر و اعلان موجودی در اکوسیستم فعلی دیده می‌شود.

### کمبودها و ریسک‌ها

1. **اطلاعات تجاری محصول کامل نیست:** برند، سازنده، بارکد، کشور سازنده، گارانتی، وضعیت نو/استوک، وزن و ابعاد، رنگ، مدل و بسته‌بندی مدل مستقل ندارند.
2. **تنوع محصول/variant وجود ندارد.** کالاهایی مانند رنگ، ظرفیت، مدل، ولتاژ یا بسته چندتایی فعلاً مدل واحد محسوب می‌شوند.
3. **قیمت برای هر variant یا تاریخ مؤثر تجاری طراحی نشده است.** تاریخچه قیمت وجود دارد، اما تاریخچه علت تغییر، کاربر تغییر‌دهنده و مرجع قیمت دیده نمی‌شود.
4. **تصاویر محصول محدود به چند URL ثابت هستند.** برای هزاران کالا نیاز به media library، alt مستقل، ترتیب، تصویر variant و thumbnail بهینه است.
5. **اطلاعات ارسال بیشتر متنی است.** هزینه و ETA باید بر اساس شهر، وزن، ابعاد، روش ارسال و موجودی واقعی محاسبه شود.
6. **مقایسه محصول، مشاهده‌شده‌های مشابه، مکمل‌ها و جایگزین‌ها باید ساختاریافته شوند.** `RelatedProductIds` به شکل comma-separated برای رشد مناسب نیست.
7. **اعتمادسازی ناقص است:** سیاست مرجوعی، گارانتی، اصالت، تأمین‌کننده، امتیاز فروشنده و موجودی واقعی باید واضح‌تر باشد.
8. **SEO محصول به کیفیت محتوا وابسته است.** توضیحات کوتاه یا تکراری برای هزاران محصول ارزش کمی ایجاد می‌کند.

### پیشنهاد حرفه‌ای

- ایجاد `ProductVariant` و `ProductAttribute`.
- جایگزینی ارتباط متنی `RelatedProductIds` با جدول رابطه‌ای.
- افزودن برند، سازنده، بارکد، MPN، GTIN/EAN، گارانتی و واحد فروش.
- افزودن وضعیت محتوا: Draft، Ready، Published، Archived.
- تعریف چک‌لیست انتشار محصول: عنوان، slug، SKU، تصویر، alt، قیمت، موجودی، مشخصات، SEO و سیاست ارسال.
- ساخت بخش «موجودی در انبار»، «تأمین مجدد»، «محصول جایگزین» و «کالاهای مکمل».

## 4.3 سبد خرید

### نقاط قوت

- سبد مهمان/کاربر در معماری فعلی پیش‌بینی شده است.
- هنگام نمایش، موجودی دوباره بررسی می‌شود.
- کالاهای ناموجود یا بیشتر از موجودی مشخص می‌شوند.
- کنترل افزایش و کاهش تعداد وجود دارد.
- آستانه ارسال رایگان نمایش داده می‌شود.
- در صورت وجود کالاهای ناموجود، حذف آن‌ها با تأیید کاربر انجام می‌شود.
- مسیر ادامه به checkout و ورود کاربر واضح است.

### ریسک‌ها و نیازها

1. قیمت داخل `CartItem` ذخیره می‌شود؛ باید روشن باشد قیمت نهایی همیشه در سرور دوباره محاسبه می‌شود و قیمت کلاینت هرگز منبع حقیقت نیست.
2. هنگام باز شدن checkout، قیمت، تخفیف و موجودی باید دوباره snapshot شوند.
3. باید رفتار تغییر قیمت بین افزودن به سبد و checkout به‌صراحت به کاربر نمایش داده شود.
4. برای کالاهای پرتقاضا، رزرو موجودی با timeout لازم است؛ فقط کم‌کردن هنگام ساخت سفارش ممکن است تجربه کاربر را پیچیده کند.
5. سبد کاربر باید برای قیمت و موجودی منقضی‌شده، پیام دقیق و قابل‌فهم بدهد.
6. دکمه «خالی کردن سبد» و حذف چند قلم باید idempotent و قابل بازیابی باشد.
7. برای آینده، سبد باید اقلام، تخفیف‌های اعمال‌شده، مالیات/هزینه، زمان آخرین اعتبارسنجی و نسخه قیمت را جدا نگه دارد.

## 4.4 checkout و ثبت سفارش

### نقاط قوت

- اطلاعات گیرنده، آدرس، روش ارسال و روش پرداخت جدا شده‌اند.
- اطلاعات قبلی checkout بازیابی می‌شود.
- کارت‌به‌کارت و درگاه آنلاین هر دو پشتیبانی می‌شوند.
- هزینه ارسال رایگان و آستانه آن نمایش داده می‌شود.
- سفارش idempotency key دارد.
- موجودی در سرور کنترل و اتمیک کم می‌شود.
- برای کاربر لاگین‌شده، اطلاعات سفارش قابل پیگیری است.

### کمبودها و ریسک‌های مهم

1. **Guest checkout باید به‌صورت سناریویی تست شود.** سفارش کاربر مهمان، دسترسی به رهگیری، اتصال بعدی به حساب و جلوگیری از افشای اطلاعات باید دقیق بررسی شود.
2. **تعریف مبلغ نهایی باید یک قرارداد یکتا داشته باشد.** در بخش‌های مختلف UI/API از `TotalAmount`، `DiscountAmount` و shipping استفاده می‌شود. باید مشخص شود `TotalAmount` قبل یا بعد از تخفیف و با یا بدون ارسال است؛ هر دو برداشت هم‌زمان، ریسک خطای حسابداری و نمایش مبلغ دارد.
3. **کد تخفیف باید در تراکنش واحد با سفارش و رزرو موجودی اعمال شود.** در غیر این صورت هم‌زمانی چند سفارش می‌تواند شمارنده یا مصرف را دچار خطا کند.
4. **محدودیت استفاده هر کاربر در مدل فعلی کامل نیست.** `CurrentUsageCount` و `MaxUsageCount` وجود دارد، اما تاریخچه مصرف per-user/order برای جلوگیری از استفاده مجدد و گزارش دقیق ضروری است.
5. **آدرس‌ها به‌صورت reusable address book دیده نمی‌شوند.** برای مشتری تکراری، ذخیره چند آدرس و آدرس پیش‌فرض لازم است.
6. **استان و شهر فعلاً هم شناسه و هم نام snapshot دارند، اما باید صحت و تغییر نام‌ها مدیریت شود.** اطلاعات سفارش تاریخی نباید با تغییر catalog جغرافیایی خراب شود.
7. **راه‌اندازی پرداخت باید state machine کامل داشته باشد:** Created، Redirected، CallbackReceived، Verified، Failed، Refunded، ManualReview.
8. **پرداخت موفق callback نباید صرفاً با پارامترهای ورودی پذیرفته شود.** مبلغ، شماره سفارش، authority/reference و وضعیت درگاه باید server-to-server verify شوند.
9. **کارت‌به‌کارت نیازمند کنترل تکراری آپلود رسید، حداکثر حجم، فرمت، اسکن و تطبیق دستی است.** فایل رسید باید خارج از release و با retention policy نگهداری شود.
10. **مالیات، کارمزد درگاه، هزینه بسته‌بندی و تعدیل مبلغ در مدل مالی فعلی جدا دیده نمی‌شوند.** حتی اگر فعلاً مالیات صفر است، باید به‌صورت explicit قابل گزارش باشد.

# 5. بررسی مدل محصول و آمادگی برای هزاران کالا

## وضعیت فعلی

`Product` شامل نام، slug، SKU اختیاری، توضیح، قیمت، تخفیف، چهار URL تصویر، دسته، موجودی ساده، featured، مشخصات فنی متنی، related IDs متنی، علائم خرابی، ETA متنی و view count است.

این مدل برای شروع سریع مناسب است، اما برای catalog بزرگ محدودیت دارد.

## کمبودهای ساختاری

### 5.1 هویت و کاتالوگ

- SKU باید unique باشد.
- slug باید unique و پایدار باشد.
- barcode/GTIN/MPN وجود ندارد.
- برند و سازنده وجود ندارد.
- دسته‌بندی درختی وجود ندارد.
- وضعیت انتشار و آرشیو وجود ندارد.
- محصول نرم‌افزاری، فیزیکی، خدمت یا bundle از هم تفکیک نشده‌اند.

### 5.2 variant

- رنگ، ظرفیت، مدل، ولتاژ، سازگاری یا بسته‌بندی مدل جدا ندارند.
- موجودی و قیمت variant مستقل نیست.
- تصویر variant مستقل نیست.

# 8. حسابداری فروشگاه

## نقاط قوت

- گزارش با بازه شمسی و presetهای امروز، ۷ روز، ماه، سال و همه وجود دارد.

- روزشمار و جزئیات روز وجود دارد.
- برای مدیر قابل استفاده و خواناست.

## مشکل بنیادی

این بخش فعلاً **گزارش فروش عملیاتی** است، نه حسابداری کامل فروشگاه. برای تصمیم مدیریتی مناسب است، اما نباید بدون تطبیق و ledger به‌عنوان دفتر مالی قطعی استفاده شود.

## مواردی که باید اصلاح معماری شوند

1. تعریف دقیق مبنای `Gross`, `Discount`, `Shipping`, `Payable`, `Confirmed`, `Net`.
2. جدا کردن مبلغ کالا از هزینه ارسال.
3. جدا کردن مبلغ پرداخت‌شده از مبلغ سفارش.
4. ثبت کارمزد درگاه و هزینه ارسال واقعی.
5. ثبت بهای تمام‌شده و سود ناخالص.
6. ثبت بدهی/طلب مشتری و وضعیت تسویه.
7. ثبت refund به‌صورت transaction مستقل.
8. ثبت adjustment با علت و تأیید دومرحله‌ای.
9. امکان تطبیق روزانه با تراکنش‌های بانکی و درگاه.
10. audit تغییرات مالی غیرقابل حذف.
11. خروجی Excel/CSV/PDF با فیلتر و گزارش قابل استناد.
12. تفکیک نقش مشاهده گزارش از ثبت/تأیید مالی.
13. جلوگیری از محاسبه کل بازه در حافظه برای بازه‌های بسیار بزرگ؛ aggregation باید تا جای ممکن در SQL یا جدول‌های روزانه انجام شود.

### ریسک مهم قابل بررسی

در چند نقطه UI و API، مبلغ نهایی با ترکیب `TotalAmount` و `DiscountAmount` محاسبه می‌شود. باید یک سند قرارداد مالی نوشته شود که دقیقاً مشخص کند:

- `TotalAmount` قبل از تخفیف است یا بعد از تخفیف؟
- shipping داخل آن است یا جدا؟
- `DiscountAmount` در چه مرحله‌ای کسر می‌شود؟
- مبلغ پرداخت واقعی کدام فیلد است؟
- refund از کدام مبنا کم می‌شود؟

تا زمانی که این قرارداد واحد نباشد، امکان اختلاف بین checkout، صفحه سفارش، حسابداری و گزارش روزانه وجود دارد.

# جمع‌بندی نهایی

فروشگاه فعلی برای راه‌اندازی و فروش واقعی، پایه‌های مناسبی دارد و بخش زیادی از مسیر اولیه را طی کرده است. مزیت اصلی آن این است که از حالت صرفاً نمایشی عبور کرده و چرخه واقعی محصول، سفارش، پرداخت، ارسال، مرجوعی و حسابداری پایه را پوشش می‌دهد.

اما برای تبدیل شدن به فروشگاه فوق‌حرفه‌ای، نباید فقط ظاهر صفحات را بیشتر کرد. اول باید چهار هسته تثبیت شوند:

1. **هسته مالی:** مبلغ نهایی، پرداخت، refund و reconciliation.
2. **هسته موجودی:** ledger، reservation، ورود/خروج و چندانبار.
3. **هسته catalog:** SKU، variant، برند، ویژگی، رسانه و workflow انتشار.
4. **هسته عملیات:** صف سفارش، SLA، bulk operation، چاپ، مرسوله و audit.

پیشنهاد قطعی این است که توسعه بعدی با **P0ها** شروع شود، سپس به‌صورت مرحله‌ای P1 و P2 اجرا شود. تا قبل از تثبیت قرارداد مالی و موجودی، افزودن قابلیت‌های ظاهری یا تبلیغات گسترده می‌تواند ریسک عملیاتی و مالی ایجاد کند.
