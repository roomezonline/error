# تحلیل گزارش سرعت DebugBear برای errorservice.ir

**منبع:** DebugBear Website Speed Test  
**تاریخ تست:** ۳ اکتبر ۲۰۲۶، ساعت ۱۳:۵۰ UTC  
**موقعیت:** US East  
**دستگاه:** شبیه‌سازی موبایل متوسط، Chrome 154، شبکه 12 Mbps و RTT برابر 70ms  
**وضعیت:** این گزارش فقط تحلیل است؛ هیچ کد یا داده‌ای تغییر نکرده است.

## خلاصه اجرایی

وضعیت فعلی از نظر سرعت **واقعاً نیازمند اصلاح است**، اما علت اصلی با یک «کم‌کردن چند کیلوبایت CSS» حل نمی‌شود. گزارش دو مشکل بزرگ را نشان می‌دهد:

1. **LCP بسیار دیر اتفاق می‌افتد:** در تست آزمایشگاهی 16.8 ثانیه و در داده واقعی CrUX حدود 8.67 ثانیه.
2. **رشته اصلی مرورگر به‌شدت درگیر است:** Total Blocking Time برابر 9.82 ثانیه و امتیاز Lighthouse برابر 44 است.

در مقابل، FCP حدود 1.95 ثانیه و Speed Index حدود 2.3 ثانیه هستند. یعنی کاربر ابتدا بخشی از صفحه را می‌بیند، اما محتوای اصلی/قهرمان صفحه بسیار دیر کامل می‌شود و JavaScript/WASM برای مدت طولانی مرورگر را مشغول نگه می‌دارد.

همچنین اختلاف مهمی بین آزمایشگاه و کاربران واقعی وجود دارد: CLS آزمایشگاهی حدود 0.02 است، ولی CLS واقعی CrUX برابر 0.41 گزارش شده. بنابراین فقط به نتیجه یک اجرای Lighthouse نباید اکتفا کرد.

## تشخیص ریشه اصلی LCP

عنصر LCP تصویر اسلایدر اصلی با عنوان «تعمیرات تخصصی» است. حجم تصویر حدود 115KB است؛ بنابراین خود حجم تصویر مشکل اصلی نیست. مشکل در زمان شروع درخواست است:

- زمان شروع درخواست تصویر LCP حدود 16.4 ثانیه ثبت شده.
- اولویت درخواست تصویر Low است.
- تصویر با `loading="lazy"` دیده شده است.
- در داده CrUX، Load Delay تصویر حدود 7.84 ثانیه است، ولی Load Duration فقط حدود 322ms است.

این یعنی سرور تصویر را بعد از شروع سریع تحویل می‌دهد، اما مرورگر خیلی دیر متوجه می‌شود که باید آن را دانلود کند. به احتمال زیاد تصویر hero بعد از اجرای Blazor، دریافت API اسلایدر و/یا رندر کامپوننت اسلایدر وارد DOM می‌شود و در عین حال lazy هم علامت خورده است.

**نتیجه:** اصلاح فرمت تصویر به‌تنهایی LCP را از 17 ثانیه به وضعیت خوب نمی‌رساند. باید تصویر hero از HTML اولیه قابل کشف باشد، برای تصویر بالای fold lazy فعال نباشد، فضای آن از ابتدا رزرو شود و درخواست آن اولویت بالا بگیرد.

## تشخیص مشکل JavaScript و Blazor WebAssembly

گزارش CPU زمان زیادی را به فایل‌های زیر نسبت می‌دهد:

- `dotnet.native...js`: حدود 5.86 ثانیه CPU
- خود صفحه/مستند اصلی: حدود 4.04 ثانیه CPU
- TinyMCE، Quill، HLS، Blazor و کتابخانه‌های نمودار نیز در بار اولیه حاضر هستند.

در waterfall نیز فایل‌های سنگین Blazor WebAssembly دیده می‌شوند:

- `dotnet.native...wasm`: حدود 906KB
- `ErrorService.Client...wasm`: حدود 835KB
- `System.Private.CoreLib...wasm`: حدود 576KB
- فایل‌های runtime و ICU نیز جداگانه دریافت می‌شوند.

علاوه بر آن، صفحه اصلی تعداد زیادی اسکریپت عمومی یا مربوط به بخش‌های تخصصی دریافت می‌کند:

- TinyMCE حدود 188KB
- HLS حدود 162KB
- Quill حدود 68.5KB
- highlight.js حدود 52.5KB
- Plyr حدود 45KB
- Chart.js حدود 67.6KB
- Hammer و chart zoom
- چندین فایل monitoring chart
- اسکریپت‌های editor، receipt، admin، chat، video و ابزارهای مختلف

این الگو نشان می‌دهد بخشی از فایل‌های مخصوص ادمین، نمودار، ویرایشگر، ویدئو یا رسید احتمالاً در layout یا bundle عمومی صفحه اصلی بارگذاری می‌شوند؛ حتی اگر کاربر در صفحه اصلی به آن‌ها نیاز نداشته باشد.

**نتیجه:** برای صفحه عمومی اصلی، کاهش JS عمومی و اجرای lazy/dynamic برای ماژول‌های تخصصی از minify کردن مهم‌تر است.

## مشکل CLS واقعی

CLS آزمایشگاهی 0.02 است، ولی مقدار واقعی کاربران 0.41 است که ضعیف محسوب می‌شود. گزارش تغییر اندازه/موقعیت ناحیه منو و محتوای اصلی را نشان می‌دهد؛ یکی از تغییرها افزایش ارتفاع حدود 494 پیکسل دارد.

علت‌های محتمل در ساختار فعلی:

- تغییر ارتفاع hero یا اسلایدر بعد از دریافت API.
- رندر دیرهنگام ناوبری، هدر یا منوی responsive.
- ورود/عدم ورود کاربر و اضافه‌شدن آیتم‌های متفاوت به منو.
- بارگذاری فونت‌ها بدون رزرو مناسب یا تغییر fallback.
- ورود محتوای dynamic از API پس از اولین paint.
- استفاده از تصاویر یا ویدئو بدون aspect-ratio/height ثابت.

**نکته مهم:** پایین‌بودن CLS در تست آزمایشگاهی به معنی سالم‌بودن تجربه همه کاربران نیست؛ مقدار CrUX باید جدی گرفته شود.

## TTFB و backend

TTFB آزمایشگاهی 1.11 ثانیه و TTFB واقعی 1.56 ثانیه است. این بخش مشکل دارد، اما نسبت به LCP و TBT اولویت دوم است.

بهبودهای مناسب برای TTFB:

- cache خروجی صفحه عمومی و داده‌های کم‌تغییر مانند تنظیمات، footer، دسته‌ها و اسلایدر.
- جلوگیری از درخواست تکراری برای `api/sitesettings` و endpointهای مشابه.
- بررسی cold start و زمان بیدارشدن سرویس هاست.
- فعال‌بودن compression مناسب و HTTP/2 یا HTTP/3 در صورت پشتیبانی هاست.
- کاهش queryهای اولیه و اجرای موازی فقط در جایی که واقعاً لازم است.
- cache کردن خروجی صفحات عمومی و invalidation فقط هنگام تغییر محتوا.

با این حال، پایین‌آوردن TTFB از 1.56 به 0.8 ثانیه به‌تنهایی مشکل LCP 8.67 ثانیه‌ای کاربران را حل نمی‌کند؛ Load Delay تصویر و CPU کلاینت عامل غالب هستند.

## درخواست‌های اضافی و تکراری

در گزارش چند endpoint با درخواست تکراری دیده می‌شود:

- `api/sitesettings` و `api/SiteSettings` چند بار
- `api/footer`
- `api/sliders/active`
- `api/categories`
- درخواست `notifications/summary` که با وضعیت 401 و `ERR_ABORTED` دیده شده است

وجود درخواست‌های worker و درخواست اصلی هم‌زمان همیشه به معنی باگ قطعی نیست، اما باید در Network trace پروژه بررسی شود. برای کاربر ناشناس، درخواست مرکز اعلان نباید در مسیر critical صفحه اصلی باعث خطا یا retry شود.

## کدام توصیه‌های DebugBear مهم‌ترند؟

### بسیار مهم

1. **Initiate LCP image requests from HTML document**
2. **Ensure LCP image is loaded with high priority**
3. **Avoid unnecessarily large یا دیررس بودن تصاویر hero**
4. **Reduce JavaScript execution time**
5. **Minimize main-thread work**
6. **کاهش فایل‌های global مربوط به TinyMCE، HLS، Quill، chart و admin**
7. **رفع تغییر ارتفاع و layout shift واقعی کاربران**

### مهم اما مرحله دوم

- cache lifetime مناسب برای فایل‌های hash شده و assetهای ثابت.
- minify CSS و JavaScript.
- حذف CSS/JS استفاده‌نشده.
- حذف زنجیره‌های `@import` در CSS.
- استفاده از TLS 1.3 در صورت امکان هاست.
- کاهش forced reflow و اجرای اسکریپت‌های DOM-heavy.

Minify کردن CSS با صرفه‌جویی تخمینی چند کیلوبایت خوب است، اما در برابر حدود 10 ثانیه blocking و 7.84 ثانیه تأخیر کشف LCP اثر اصلی ندارد.

## ارتباط با ساختار پروژه فعلی

با توجه به ساختار پروژه، این نتیجه با چند ویژگی فعلی هم‌خوان است:

- پروژه Blazor WebAssembly است و runtime WASM در بار اولیه هزینه قابل توجهی دارد.
- امکانات نمودار، ویدئو، editor، پیام‌رسانی، receipt و مدیریت در پروژه وجود دارد؛ اگر script آن‌ها در layout عمومی قرار گرفته باشد، صفحه اصلی هزینه همه آن‌ها را پرداخت می‌کند.
- برای hero و slider، تصویر از مسیر uploads و از داده محتوایی دریافت می‌شود؛ همین می‌تواند discovery تصویر را به بعد از API و hydration منتقل کند.
- سیستم SEO و fallback موجود است، بنابراین فرصت مناسبی برای تولید HTML اولیه سبک‌تر و قابل مشاهده برای صفحه عمومی وجود دارد.

## برنامه اصلاح پیشنهادی، بدون ریسک برای داده

### فاز 1 — اصلاح LCP و اندازه layout

هدف این فاز رساندن LCP اولیه به کمتر از 3 تا 4 ثانیه در تست موبایل است.

- تصویر hero فعلی بالای fold از lazy خارج شود.
- تصویر اصلی در HTML اولیه یا با preload/priority hint قابل کشف شود.
- برای hero، `width`، `height` یا `aspect-ratio` ثابت اعمال شود.
- اولین اسلاید قبل از فعال‌شدن slider نمایش داده شود.
- اسلایدهای بعدی و تصاویر غیرقابل مشاهده lazy بمانند.
- اگر تصویر از API می‌آید، fallback سبک و ثابت برای اولین paint در نظر گرفته شود.
- تغییر ارتفاع header، menu و hero بعد از load حذف شود.

### فاز 2 — سبک‌سازی shell عمومی

- فهرست scriptهای layout و index صفحه بررسی شود.
- TinyMCE، Quill، HLS، Plyr، highlight.js، html2canvas، Chart.js و فایل‌های monitoring فقط در route/کامپوننت لازم load شوند.
- فایل‌های admin و chart از صفحه عمومی اصلی حذف شوند.
- اسکریپت‌های کم‌اهمیت با `defer` یا dynamic import اجرا شوند.
- درخواست اعلان برای کاربر ناشناس از مسیر critical حذف یا بعد از load اجرا شود.
- درخواست‌های تکراری تنظیمات، footer، categories و sliders با cache client/server یک‌بار شوند.

### فاز 3 — بهینه‌سازی WASM

- trimming و انتشار Release بررسی شود.
- Brotli یا compression صحیح برای WASM فعال و با headerها تأیید شود.
- قابلیت lazy loading یا جداکردن assemblyها برای بخش‌های کم‌مصرف بررسی شود.
- صفحات عمومی مهم تا حد امکان HTML اولیه/SSR یا prerender سبک داشته باشند.
- بارگذاری runtime برای کاربر ناشناس تا حد امکان به بعد از محتوای اصلی منتقل شود.

### فاز 4 — اصلاح تجربه واقعی کاربران

- CLS واقعی در CrUX و RUM به‌صورت هفتگی پایش شود.
- تست با موبایل ضعیف، شبکه 3G/4G و کاربر سرد/گرم انجام شود.
- صفحات اصلی، محصولات، کدهای خطا و فروشگاه جداگانه تست شوند؛ نتیجه صفحه خانه نماینده همه سایت نیست.
- بعد از هر تغییر، Lighthouse پنج بار اجرا و median ثبت شود؛ یک اجرای منفرد معیار کافی نیست.

## جمع‌بندی نهایی

گزارش DebugBear معتبر و هشدار آن جدی است؛ امتیاز 44 و Good CrUX برابر 12٪ نشان می‌دهد تجربه بخشی از کاربران واقعاً ضعیف است. بااین‌حال، مشکل را نباید فقط به «سرعت هاست» یا «حجم تصویر» نسبت داد.

**سه علت اصلی به ترتیب اهمیت:**

1. تصویر hero دیر کشف می‌شود و به اشتباه lazy/Low priority است؛
2. Blazor WebAssembly و bundleهای عمومی، به‌علاوه کتابخانه‌های تخصصی، CPU زیادی مصرف می‌کنند؛
3. layout در تجربه واقعی کاربران پس از load جابه‌جا می‌شود و CLS واقعی را بالا می‌برد.

بنابراین اولین اقدام فنی باید audit و اصلاح مسیر LCP و layout عمومی باشد، نه دست‌کاری دیتابیس، چارت‌های مانیتورینگ یا سیستم سفارش. پس از آن باید scriptهای غیرضروری صفحه اصلی جدا شوند و در پایان TTFB و cache بهینه شوند.
