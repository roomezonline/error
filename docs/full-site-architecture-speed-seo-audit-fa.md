# گزارش جامع تحلیل کل سایت ErrorService

## محدوده و روش بررسی

این گزارش فقط بر اساس بررسی سورس فعلی پروژه، ساختار صفحات، pipeline سرور، فایل‌های استاتیک، مسیرهای عمومی، APIها، مدل‌های داده و تنظیمات موجود تهیه شده است.

- هیچ کد یا داده‌ای در این مرحله تغییر نکرده است.
- امتیازها «وضعیت فنی قابل مشاهده در سورس» هستند، نه نتیجه قطعی Core Web Vitals زنده یا Search Console.
- برای امتیاز قطعی سرعت باید تست موبایل و دسکتاپ روی دامنه زنده، چند مسیر واقعی، چند شبکه و چند نوبت انجام شود.
- برای امتیاز قطعی ایندکس باید Google Search Console، Coverage، Page Indexing، Crawl Stats و URL Inspection بررسی شوند.

# 3. مشکلات قطعی و هشدارهای بسیار مهم

## 3.1 اطلاعات حساس در فایل تنظیمات — بحرانی

در `appsettings.json` و `appsettings.Development.json` اطلاعات اتصال دیتابیس و کلید JWT به‌صورت مستقیم وجود دارد. این فایل‌ها در مسیر پروژه و همراه سورس قرار دارند.

### ریسک

- هر فردی که به repository، backup، zip انتشار، لاگ یا فایل پروژه دسترسی پیدا کند، ممکن است به دیتابیس یا توکن‌ها دسترسی بگیرد.
- قرار داشتن اطلاعات دیتابیس واقعی در تنظیمات Development بسیار خطرناک است.
- `AllowedHosts` نیز بسیار باز تنظیم شده است.

### امتیاز امنیتی این بخش: **2 از 10**

این مهم‌ترین هشدار کل ممیزی است. حتی اگر فعلاً هیچ تغییر کدی انجام نشود، باید در برنامه امنیتی پروژه برای چرخش رمز دیتابیس و کلید JWT، حذف secrets از سورس و استفاده از environment/hosting secrets قرار گیرد.

## 3.2 تعداد زیاد تغییرات ثبت‌نشده در Git

وضعیت فعلی پروژه شامل تعداد زیادی فایل modified و untracked است؛ از صفحات اصلی و فروشگاه تا Program، DbContext، migrationها، سرویس‌ها و فایل‌های JavaScript.

### ریسک

- مشخص نیست کدام تغییرات نهایی و کدام آزمایشی هستند.
- rollback امن دشوار می‌شود.
- ممکن است انتشار ناقص، ترکیبی یا دارای migration ناسازگار رخ دهد.
- مقایسه نسخه زنده با نسخه محلی سخت می‌شود.

### نتیجه

پیش از هر توسعه بزرگ، باید baseline مشخص، commitهای کوچک، release tag و فهرست migrationهای قابل انتشار وجود داشته باشد.

## 3.3 اجرای migration در startup

در تنظیمات، `ApplyMigrationsOnStartup` فعال است و برنامه در startup می‌تواند `Database.Migrate()` اجرا کند.

### ریسک

- lock دیتابیس یا خطای transient می‌تواند کل سایت را از startup بیندازد.
- migration سنگین در زمان deploy باعث downtime می‌شود.
- اگر دو instance هم‌زمان بالا بیایند، احتمال رقابت وجود دارد.

برای محیط production، migration باید بخشی از deployment کنترل‌شده با backup و rollback باشد، نه وابسته به اولین request/startup سایت.

## 3.4 Blazor WASM و HTML اولیه

بخش زیادی از سایت روی Blazor WebAssembly است. برای SEO، fallback/prerender اضافه شده، اما کیفیت index همچنان به این موارد وابسته است:

- پاسخ مستقیم سرور برای هر URL
- محتوای واقعی همان رکورد در HTML اولیه
- status code صحیح برای 404
- نبود محتوای تکراری
- دسترسی crawler به CSS، JS، تصویر و APIهای لازم

اگر یک صفحه رکوردی فقط بعد از اجرای JS محتوای اصلی را دریافت کند، از نظر گوگل ممکن است ضعیف‌تر از صفحه‌ای باشد که HTML کامل اولیه دارد.

# 4. تحلیل ساختار و معماری

## نقاط قوت

- تفکیک Client، Server و Shared مناسب است.
- لایه‌های Controllers، Services، Models، Data و Infrastructure قابل تشخیص هستند.
- دامنه‌های کسب‌وکار اصلی تقریباً مشخص‌اند.
- برای auth، payment، notification، monitoring و SEO سرویس‌ها و اجزای اختصاصی وجود دارد.
- مدل‌های جدید با migrationهای جداگانه اضافه شده‌اند.
- مسیرهای legacy WebForms در کنار سیستم جدید مدیریت شده‌اند.

## نقاط ضعف

1. **دامنه پروژه بسیار بزرگ شده است.** فروشگاه، تعمیرات، آموزش، مانیتورینگ و CRM در یک برنامه واحد قرار دارند؛ این موضوع سرعت توسعه و تست را کاهش می‌دهد.
2. **برخی controllerها بسیار بزرگ و چندمسئولیتی هستند.** مخصوصاً سفارش و کنترلرهای Store. این کار تغییرات بعدی را پرریسک می‌کند.
3. **وجود پروژه/پوشه‌های legacy، publish، obj، bin و فایل‌های موقت مدیریت release را سخت می‌کند.**
4. **قراردادهای DTO در برخی حوزه‌ها رشد کرده‌اند اما versioning API مشخصی دیده نمی‌شود.**
5. **منطق business در controllerها زیاد است.** محاسبه سفارش، تخفیف، موجودی، رسید و اعلان بهتر است به application serviceهای مجزا منتقل شوند.
6. **برای کارهای سنگین queue استاندارد سراسری دیده نمی‌شود.** اعلان، export، پردازش تصویر، شمارنده بازدید و گزارش‌های بزرگ در آینده نیازمند background processing هستند.
7. **observability باید یکپارچه‌تر شود:** correlation ID، structured logging، metrics، tracing و alert عملیاتی.
8. **تست خودکار گسترده در شواهد فعلی دیده نمی‌شود.** با این تعداد قابلیت، نبود integration test ریسک مهم است.

# 5. تحلیل سرعت و عملکرد

## نقاط قوت عملکردی

- فشرده‌سازی پاسخ فعال است.
- cache برای assetها با تفکیک فایل‌های immutable و stable در نظر گرفته شده است.
- Output Cache وجود دارد.
- تصاویر در بسیاری از صفحات lazy load هستند.
- API محصولات و سفارش‌ها pagination دارند.
- روی نمودارهای مانیتورینگ، استراتژی progressive loading و decimation طراحی شده است.
- responseهای API عموماً projection به DTO دارند.
- rate limit از abuse ساده جلوگیری می‌کند.

## مشکلات و گلوگاه‌های محتمل

### 5.1 حجم اولیه کلاینت

در `wwwroot` مجموعه بزرگی از vendorها وجود دارد، از جمله TinyMCE با pluginها و themeهای متعدد، Chart.js، HLS، Plyr، Quill، Highlight.js و چند مجموعه فونت.

حتی اگر همه این فایل‌ها در صفحه اول دانلود نشوند، باید بررسی شود که در layout عمومی چه تعداد از آن‌ها بدون نیاز واقعی load می‌شوند. TinyMCE، ادیتورهای محتوا و chart library نباید برای کاربر عادی سایت در مسیر home و product بارگذاری شوند.

### 5.2 چند خانواده فونت

فونت‌های Vazirmatn، Vazir، Shabnam و Sahel هم‌زمان در پروژه وجود دارند. این موضوع می‌تواند:

- تعداد requestها را زیاد کند.
- حجم CSS و font را افزایش دهد.
- باعث اختلاف layout و FOUT/FOIT شود.
- انتخاب فونت را در صفحات مختلف ناهماهنگ کند.

### 5.3 فایل‌های بدون version در CSS/JS

`no-cache` باعث می‌شود نسخه جدید سریع‌تر دیده شود، اما هر بار revalidation انجام می‌شود و برای assetهای بزرگ ایده‌آل نیست. راهکار حرفه‌ای‌تر، fingerprint/version hash برای فایل‌های CSS/JS و cache طولانی برای فایل‌های immutable است.

### 5.4 تصاویر و فایل‌های آپلودی

پروژه مسیرهای متعدد upload دارد: محصول، اسلایدر، خبر، داستان، سنسور، کارگاه و رسید. اگر تصاویر resize، thumbnail، WebP/AVIF، محدودیت ابعاد و CDN نداشته باشند، بیشترین سهم LCP و مصرف هاست را ایجاد می‌کنند.

### 5.5 queryهای سنگین

در کد الگوهای زیر نیاز به پایش جدی دارند:

- `ToListAsync` روی بازه‌های بزرگ
- گزارش حسابداری بازه‌های طولانی که ابتدا ردیف‌ها را به حافظه می‌آورد
- جست‌وجوی `ToLower().Contains()` روی سفارش و محصول
- `OrderBy(Guid.NewGuid())` برای انتخاب تصادفی محصولات
- `Include`های عمیق در صفحات مدیریتی
- شمارش و جمع‌زدن‌های متعدد برای dashboard

این موارد در داده کم خوب هستند، اما با رشد فروشگاه یا گزارش یک‌ساله می‌توانند CPU، RAM و زمان پاسخ را بالا ببرند.

### 5.6 Blazor WASM در موبایل

مشکل اصلی سرعت سایت احتمالاً فقط TTFB نیست؛ هزینه parse/compile/execute فایل‌های WASM و JS نیز مهم است. برای موبایل باید مسیرهای عمومی از admin و ابزارهای سنگین جدا شوند.

### امتیاز سرعت بر اساس کد: **6.9 از 10**

# 6. تحلیل SEO فنی

## نقاط قوت

- title و description در صفحه اصلی و بخش‌های مهم وجود دارد.
- canonical برای صفحات تخصصی و کد خطا تولید می‌شود.
- hreflang فارسی/x-default برای صفحه اصلی وجود دارد.
- Open Graph و Twitter metadata دیده می‌شود.
- JSON-LD برای Organization، WebPage، Breadcrumb، Product و برخی صفحات تخصصی وجود دارد.
- صفحه کد خطا URL خوانا و جزئی دارد:
  `/technical/error-codes/{brand}/{deviceType}/{code}`
- صفحه سنسور URL جزئی دارد:
  `/technical/sensor-finder/{id}`
- headingهای اصلی صفحات مهم وجود دارند.
- تصاویر بخش‌های زیادی alt دارند.
- محتوای آکادمی و اخبار از نظر SEO ظرفیت بالایی دارد.
- prerender مخصوص crawler برای کاهش وابستگی به اجرای JS ایجاد شده است.

## ضعف‌های فنی و محتوایی

### 6.1 صفحات رکوردی باید HTML واقعی داشته باشند

برای هر کد خطا و سنسور، گوگل باید بدون تعامل کاربر بتواند این موارد را در پاسخ اولیه ببیند:

- نام و عنوان دقیق
- توضیح منحصربه‌فرد
- برند/نوع دستگاه
- راه‌حل یا مشخصات واقعی
- لینک‌های داخلی مرتبط
- تصویر با alt
- canonical دقیق
- JSON-LD معتبر

اگر prerender فقط برای برخی مسیرها یا با fallback عمومی اجرا شود، ممکن است صفحات رکوردی در crawl دیده شوند اما محتوای کافی نداشته باشند.

### 6.2 ریسک صفحات کم‌محتوا و تکراری

صفحه رکوردی که فقط نام سنسور، یک تصویر و متن کوتاه دارد، ممکن است از نظر گوگل «thin content» محسوب شود. زیاد بودن URL به‌تنهایی باعث index شدن نمی‌شود.

### 6.3 sitemap و لینک‌دهی داخلی

هر رکورد ارزشمند باید:

- در sitemap مناسب قرار گیرد.
- از صفحات hub و دسته‌بندی لینک داخلی داشته باشد.
- به رکوردهای مرتبط لینک دهد.
- تاریخ آخرین تغییر معتبر داشته باشد.
- رکورد حذف‌شده status مناسب بگیرد.

صفحات زیادی که فقط در sitemap هستند اما از سایت لینک داخلی ندارند، discoverability پایین‌تری خواهند داشت.

### 6.4 canonical و پارامترها

فیلترهای query string، جست‌وجو، مرتب‌سازی و pagination باید سیاست مشخص داشته باشند. در غیر این صورت duplicate URL، crawl waste و canonicalهای متناقض ایجاد می‌شود.

### 6.5 hreflang

سایت فعلاً فارسی است. hreflang فارسی و x-default مفیدند، اما اگر نسخه زبان دوم واقعی وجود ندارد، نباید URLهای جعلی زبان تولید شود. hreflang باید در همه صفحات قابل index، با canonical هم‌راستا باشد.

### 6.6 structured data

JSON-LD باید با محتوای قابل مشاهده یکسان باشد. در فروشگاه باید Product، Offer، AggregateRating و Breadcrumb فقط زمانی درج شوند که داده واقعی، معتبر و قابل مشاهده وجود داشته باشد.

### 6.7 alt و تصاویر

در کدهای جدید alt وضعیت خوبی دارد، اما با توجه به تعداد زیاد componentها باید به‌صورت build/lint سراسری کنترل شود. لوگو و تصاویر تزئینی باید alt خالی یا alt معنادار صحیح داشته باشند؛ تصویر بدون alt برای SEO و accessibility مشکل‌ساز است.

### امتیاز SEO فنی: **7.5 از 10**

# 7. تحلیل آمادگی ایندکس گوگل

## بخش‌های دارای شانس خوب برای ایندکس

- اخبار و مقالات
- آموزش‌ها و درس‌ها
- صفحات کد خطای دارای محتوای واقعی
- صفحات دسته‌بندی و hubهای محتوایی
- صفحات محصولی با توضیح منحصربه‌فرد، تصویر و مشخصات کامل

## بخش‌هایی که احتمال ایندکس ضعیف‌تری دارند

- سنسورهایی با توضیح کوتاه یا محتوای تکراری
- رکوردهایی که فقط در API بعد از اجرای JS لود می‌شوند
- صفحات محصول بدون توضیح کافی یا اطلاعات تکراری
- URLهای جست‌وجو و فیلتر
- صفحات pagination کم‌ارزش
- صفحات admin، پروفایل، cart، checkout و محتوای خصوصی
- رکوردهای حذف‌شده که redirect/410 مشخص ندارند
- URLهایی که فقط در sitemap هستند و لینک داخلی ندارند

## برآورد امتیاز ایندکس

**6.6 از 10 برای آمادگی فنی**

این عدد به معنی درصد صفحات ایندکس‌شده نیست. درصد واقعی فقط با Search Console مشخص می‌شود. در پروژه، زیرساخت لازم وجود دارد، اما برای رسیدن به index بالا باید کیفیت، یکتایی و دسترسی HTML هر رکورد تضمین شود.

## عوامل محتمل افت index

1. محتوای کم‌حجم یا مشابه در رکوردهای دیتابیس.
2. prerender ناقص یا پاسخ دیرهنگام برای crawler.
3. sitemap بزرگ یا دارای URLهای کم‌ارزش.
4. نبود لینک داخلی کافی به رکوردها.
5. canonical اشتباه در مسیرهای رکوردی.
6. پاسخ 200 برای صفحه‌ای که رکورد ندارد، به‌جای 404.
7. نبود مدیریت 301/410 برای slug یا رکورد حذف‌شده.
8. کندی server rendering/API برای حجم زیاد رکورد.
9. محتوای تکراری در title و description.
10. خطاهای crawl در فایل‌های JS/CSS/image یا محدودیت منابع.

# 8. مشکلات و باگ‌های محتمل بر اساس بررسی کد

> موارد این بخش از روی کد شناسایی شده‌اند و بعضی برای اثبات نهایی نیازمند تست runtime هستند.

## باگ/ریسک بحرانی

- secrets واقعی در appsettings.
- migration خودکار در startup.
- احتمال exposure اطلاعات حساس در backup، publish یا repository.
- تغییرات زیاد بدون commit baseline.

## ریسک‌های عملکردی

- queryهای بزرگ حسابداری در حافظه.
- جست‌وجوی غیرقابل استفاده از index در بعضی مسیرها به‌علت `ToLower().Contains()`.
- random sorting با Guid برای فهرست محصولات.
- بارگذاری احتمالی vendorهای سنگین در layout عمومی.
- تعدد فونت‌ها و assetهای ثابت.
- export و گزارش‌گیری بدون job/queue برای بازه‌های بزرگ.

## ریسک‌های SEO

- ممکن است بعضی URLهای رکوردی prerender کامل نداشته باشند.
- امکان تکراری بودن title/description رکوردها.
- نیاز به بررسی status code رکورد ناموجود.
- نیاز به کنترل sitemap و لینک داخلی برای همه رکوردهای مهم.
- احتمال اختلاف محتوای JSON-LD با متن قابل مشاهده.

## ریسک‌های کسب‌وکاری/مالی

- قرارداد تعریف `TotalAmount`, `DiscountAmount`, shipping و مبلغ پرداخت نهایی باید یکسان‌سازی شود.
- پرداخت و callback به تست idempotency، verify و reconciliation دقیق نیاز دارد.
- موجودی ساده Product برای چندانبار و reservation آینده کافی نیست.
- حسابداری فعلی بیشتر گزارش فروش است و ledger رسمی نیست.
- حذف واقعی محصول/کوپن/دسته ممکن است تاریخچه یا لینک‌ها را آسیب‌پذیر کند.

## ریسک‌های نگهداری

- controllerهای حجیم.
- نبود شواهد کافی از integration test جامع.
- وجود فایل‌های temporary و خروجی build در ریشه پروژه.
- هم‌زیستی مسیرهای legacy و جدید.
- نبود سیاست واضح برای نسخه‌بندی API و migration deployment.

# 11. نتیجه نهایی

ErrorService یک پروژه **بزرگ، فعال و چندمنظوره** است که از نظر امکانات از بسیاری سایت‌های ساده جلوتر است. مهم‌ترین مزیت آن breadth زیاد امکانات و وجود تلاش‌های واقعی برای performance، SEO، monitoring و عملیات فروشگاه است.

با این حال، سایت هنوز برای رسیدن به سطح «کاملاً حرفه‌ای و مقیاس‌پذیر» به سه کار پایه نیاز دارد:

1. **امنیت و کنترل انتشار:** حذف secrets از config، baseline Git، rollback و migration deployment امن.
2. **اندازه‌گیری واقعی:** تست زنده سرعت و Search Console، نه فقط اتکا به بررسی سورس.
3. **تکمیل هسته‌ها:** جست‌وجو، مدل محصول، موجودی، پرداخت، حسابداری و HTML اولیه صفحات رکوردی.

### حکم نهایی

- **از نظر امکانات:** قوی
- **از نظر ایده و پوشش کسب‌وکار:** بسیار خوب
- **از نظر آماده‌سازی برای SEO:** خوب، اما نه تضمین‌شده
- **از نظر سرعت:** قابل قبول، با چند گلوگاه مهم
- **از نظر امنیت فعلی:** نیازمند رسیدگی فوری
- **از نظر مقیاس‌پذیری:** مناسب رشد مرحله‌ای، نه هنوز آماده رشد نامحدود
- **امتیاز کل فعلی:** **6.9 از 10**

این امتیاز با رفع P0های امنیتی و استقرار و سپس بهینه‌سازی assetها، prerender رکوردی و queryهای بزرگ، واقع‌بینانه می‌تواند به حدود **8.2 تا 8.7 از 10** برسد.
